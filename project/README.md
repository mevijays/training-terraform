# Capstone Project — Multi-Environment, Multi-Cloud Platform Stack

## Goal

Build a realistic, production-shaped Terraform codebase that touches every topic in the course. By the end you should be able to take an empty Azure + AWS account and stand up dev / stage / prod environments, each with shared modules and remote state in HCP Terraform.

## Scenario

You're the platform engineer for a fictional company **"NovaPay"**, a fintech that runs a customer-facing API.

- Engineering wants three environments: `dev`, `stage`, `prod`.
- Networking must live in Azure (existing investment).
- Object storage and a static marketing site must live in AWS (compliance choice).
- Secrets live in Azure Key Vault.
- Everything is provisioned via HCP Terraform with PR-based plans.

## Architecture target

```
                  ┌──────── HCP Terraform ─────────┐
                  │   workspace per env, tagged    │
                  │   variable set: cloud creds    │
                  │   sentinel/OPA policy: prod    │
                  └──────────────┬──────────────────┘
                                 │
       Azure (per env)           │            AWS (per env)
   ┌────────────────────┐        │       ┌──────────────────────┐
   │ resource group     │        │       │ S3 bucket (artifacts)│
   │ ├ vnet/subnets     │        │       │ S3 + CloudFront      │
   │ ├ NSG              │        │       │   (static site)      │
   │ ├ Key Vault (sec)  │        │       │ Route53 zone         │
   │ ├ Linux VM (web)   │        │       └──────────────────────┘
   │ └ Log Analytics    │        │
   └────────────────────┘        │
```

## Phases

Work through these in order. Each phase intentionally pulls from specific course modules.

### Phase 1 — Bootstrap (modules 2, 3, 4, 11)

- Create an HCP Terraform organization and a project called `novapay`.
- Create a variable set with Azure and AWS credentials (or set up OIDC).
- Create three workspaces: `novapay-dev`, `novapay-stage`, `novapay-prod`, each tagged with its env.

### Phase 2 — Networking module (modules 5, 6, 7, 9)

- Build `modules/azure-network` that takes:
  - `name`, `address_space`, `subnets = map(string)`, `tags`.
- Outputs `vnet_id`, `subnet_ids`.
- Use `for_each` for subnets.
- Apply for `dev` first.

### Phase 3 — Secrets and Key Vault (modules 13, 14)

- Build `modules/azure-keyvault`.
- Use `validation` blocks on variables (env, location).
- Use `precondition` to require prod to be deployed only in westeurope.
- Add a sample secret (DB password) generated by `random_password`, marked `sensitive`.
- Bonus: refactor to use `ephemeral` + write-only when stored into a VM.

### Phase 4 — Compute (modules 8, 9)

- Build `modules/azure-vm` that takes the network module's outputs.
- Use `lifecycle { create_before_destroy = true }` on the VM.
- Use `ignore_changes` for `os_disk.id`.
- Cloud-init runs a small Python web app.

### Phase 5 — AWS static site (modules 3, 9)

- Build `modules/aws-static-site` that takes a domain name and creates:
  - An S3 bucket (private).
  - A CloudFront distribution.
  - A Route 53 record.
- Outputs the CloudFront URL.

### Phase 6 — Observability (module 9)

- Build `modules/observability` for Log Analytics and diagnostic settings.
- Apply to all environments.

### Phase 7 — Refactor with `moved` (module 12)

- Rename one module call (e.g. `module.vnet` → `module.network`). Use a `moved` block to do it safely.
- Demonstrate drift detection: change a tag in the portal, then `terraform plan -refresh-only`.

### Phase 8 — Policy (module 16)

- Write a Sentinel or OPA policy that:
  - Requires all resources to have `env` and `owner` tags.
  - Forbids resources outside `eastus`, `westus2`, `westeurope`.
  - Forbids public S3 buckets.
- Attach to the prod workspace as `hard-mandatory`.

### Phase 9 — Promote dev → stage → prod (module 17)

- Set up run triggers: dev apply → stage plan.
- Walk through the full path from a PR to prod apply.

## Acceptance criteria

When you're done:

- [ ] All three envs apply cleanly.
- [ ] `terraform state list` shows resources you expect, with module prefixes.
- [ ] No secrets in state for the DB password.
- [ ] At least one `moved` block was used.
- [ ] At least one `prevent_destroy` is on a critical resource.
- [ ] A `check` block monitors the web app's `/healthz` endpoint.
- [ ] A policy fails a sample bad PR.
